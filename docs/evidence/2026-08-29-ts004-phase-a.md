# TS-004 Phase A service evidence

- **Date:** 2026-08-29
- **Scope:** Minimal ASP.NET Core host/configuration/health scaffold
- **Boundary:** Hyper-V development VM on the temporary Default Switch
- **Result:** Phase A accepted; TS-004 remains in progress

## Implemented boundary

The service targets .NET 8 and exposes /api/health. Its configuration has a
validated instance-name boundary. The only registered server-radio status
implementation reports operational false, radio unavailable, and reason
not-configured.

No USB framing, packet, transmit, receive, queue, retry, database, or hardware
success behavior is implemented or claimed.

Docker Compose keeps the service in its own network namespace and publishes its
HTTP port only to host loopback. Caddy exposes the health route through the
already accepted LAN HTTP port. Direct access to the container port is not
permitted from Windows.

## Validation

- Release build completed with zero warnings and zero errors.
- Host-profile and service-scaffold static checks passed.
- Repository lint passed and the existing web prototype built successfully.
- A local live request returned HTTP 200 with operational false and radio
  unavailable.
- The exact source bundle built and started on the first TS-002 VM.
- verify-app.sh returned TRAIL_SERVER_APP_RESULT=PASS.
- Restarting nftables with the container running also restarted Docker in the
  required order; the container returned and both application and host
  verifiers passed.
- After a full VM reboot, Windows reached SSH and Caddy port 80, received the
  bounded health response, and could not connect directly to port 5080.

The temporary Hyper-V address changed across reboot. This is expected on the
Default Switch and does not satisfy TS-002's final router-reserved external-LAN
acceptance.
